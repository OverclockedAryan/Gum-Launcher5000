# DESUU: face-tracking gum-launcher desk robot

Context for Claude Code sessions: this file is the map and the rules; the details live in `docs/`. When a decision or a number changes, update the doc **and** this summary.

## What we're building

A friendly, 3D-printed desktop robot with a camera in its turret head. It tracks a person's face at 0.5–2 m. When they opt in (eyebrows up) and then hold their mouth open for 300 ms, it tosses one hard-coated gum pellet into their mouth. Hardware and software are built from scratch, at home, in India.

## Safety invariants

Never violate these in code, firmware or hardware.

1. **Hardware chain.** The ARM switch and E-stop sit in series with actuator power. Nothing may bypass them, and firmware never emulates "armed".
2. **One firing path.** Firing goes only through the fire-control state machine, and every gate in REQ-SAF-001 must pass in the same frame. No debug or back-door FIRE path, including in manual trick-shot mode.
3. **Eyes.** Safety is judged on the predicted impact zone (3σ plus the worst allowed over-speed) against live eye landmarks + 15 mm. Never shrink that margin, the 5 mm aim-below offset or the short range bias to "improve hit rate".
4. **Energy.** ≤ 40 mJ physically for the heaviest configured pellet; ≤ 30 mJ operating. The chronograph locks out above +8 % or on 2 % drift. No code may raise the spring preload beyond the verified cap.
5. **Consent and pacing.** An open mouth alone never fires: an explicit opt-in opens a 5 s window for one shot. Shots to one person are ≥ 10 s apart, at most 5 per session, and the mouth must close between shots.
6. **Safe defaults.** Boot, reset and every fault go to SAFE; re-arming needs the switch cycled; nothing auto-resumes. The spring decocks when idle, and the breech empties without power.
7. **Microcontroller checks of its own.** It independently enforces the armed rail, a 200 ms heartbeat timeout, single-use fresh FIRE tokens, chambered and parked, a 5 s minimum interval, and a watchdog.
8. **No lasers.** Range sensors only as unmodified Class 1 modules.
9. **Tests.** Any change to the gates or interlocks ships with tests (100 % branch coverage of fire control) and a note in docs/safety.md.
10. **People.** Anyone in front of an armed robot wears impact-rated glasses until M6; armed testing starts on printed face targets.

## Architecture in one screen

- **Compute board:** Raspberry Pi 5 1 GB running Trixie Lite and Python 3.13, with an OV5647 CSI camera (D-007; buy last, out of stock in India). It handles the camera, MediaPipe FaceLandmarker, range estimate, ballistics table, aim controller, fire control, modes, UI and sound.
- **Microcontroller** (the owner's Pico or ESP32): turret steppers (step pulses, ramps, homing), launcher motor (JGY370 worm through a TB6612FNG), shuttle servo (MG90S), chamber IR, chronograph gates (edge timestamps), cam switch, ARM-rail sensing, watchdog, eyes (2× GC9A01, or WS2812 to save money).
- **Link:** USB serial carrying a line protocol with sequence numbers and CRC8, plus a 20 Hz heartbeat ([protocol](docs/architecture.md#microcontroller-protocol-draft)).
- **Camera** sits on the turret head, tilted about 10° down from the barrel (D-003). Visual servoing holds the mouth at a range-dependent offset below the barrel axis, and the camera-on-head arrangement cancels gear play.
- **Launcher** (D-001): a snail-cam spring push sled. The pellet rides the sled from the start (push, never hit), and a bumper stops the sled. A self-locking JGY370 worm cocks it, and reversing the cam decocks it.
- **Feed** (D-006): an orientation-locking stack above a spring-return shuttle, with a chamber IR sensor. A jam triggers reverse, retry, then fault.
- **Power:** 12 V 5 A in → fuse → 5 V buck for logic; the E-stop feeds the turret rail, and the ARM switch feeds the launcher rail.

## Conventions

- **Python:** ≥ 3.11, type hints, dataclasses. SI units inside (m, s, rad, kg). Put units in names (`range_m`, `pan_deg`, `t_ms`); degrees appear only at config and UI boundaries.
- **Hardware abstraction:** all hardware sits behind interfaces with fakes. A feature runs on the Windows PC with a webcam and `--sim` before it touches hardware.
- **Traceability:** cite requirement IDs in code and tests (`# REQ-SAF-002`). Decisions change only by adding a new D-entry.
- **Config:** tunables in `config/desuu.yaml`, per-robot calibration in `config/calibration.yaml`. Never hard-code calibration.
- **Shot log:** one JSON line per shot (time, range, angles, gate results, measured speed) under `logs/`.
- **Research:** keep sources and mark claims (unverified) or (estimate). Prices go stale fast: re-check before ordering.
- **Ballistics:** after changing an assumption, run `python tools/ballistics_sim.py --out docs/research/ballistics.md`. It takes about 10 s, and every assumption is a flag.
- **Git:** commit only when the owner asks.

## Implementation gotchas

Sources: [vision-compute.md](docs/research/vision-compute.md), [compute-camera-india.md](docs/research/compute-camera-india.md).

**MediaPipe**

- Use the Tasks `FaceLandmarker` only: `mp.solutions` (face_mesh) was removed in 0.10.30.
- Use `mediapipe` ≥ 1.1 on Python 3.13. Release 1.2.x renamed some Tasks fields and kept deprecated aliases.
- Ignore old tutorials that pin 0.10.18 or run Bookworm.
- Run in VIDEO mode, with your own capture thread. LIVE_STREAM has reports of hanging.
- On Linux, inference runs on one thread. Extra worker processes raise FPS but don't cut per-frame latency.
- The built-in BlazeFace detector letterboxes the frame to 128 px, so a face at 2 m is about 7–9 px. Feed it a centre or tracked crop (or use full-range BlazeFace or YuNet to find the face first).
- For aiming precision, give the landmarker a full-resolution face crop, not a frame downscaled to 640 px.

**Face landmarks and distance**

- Landmark indices: inner lips 13 (upper) and 14 (lower); inner mouth corners 78 and 308; iris centres 468 and 473.
- Starting mouth rule: open when `jawOpen ≥ 0.45` and MAR ≥ 0.35; closed when `jawOpen < 0.30` or MAR < 0.25. Calibrate per person.
- The facial-matrix depth assumes a 63° vertical FOV. Rescale it by `tan(31.5°) / tan(VFOV_real/2)`.
- Range needs per-person calibration. Uncalibrated cues are about 4–6 % off, against a 2.5 % budget.

**Raspberry Pi 5 setup**

- Create the venv with `--system-site-packages`, because picamera2, libcamera and lgpio come only from apt.
- pip's OpenCV 5.1 needs NumPy ≥ 2. Trixie is fine; Bookworm breaks.
- Picamera2 uses DRM format names: `RGB888` is B,G,R byte order, so request `BGR888` for RGB and verify it.
- pigpio doesn't work on the Pi 5, and lgpio PWM is software-timed. All actuators go through the microcontroller anyway.
